# JSON 存储改造方案与实施计划

日期：2026-10-17。目标：最终主程序彻底移除 SQLite，保留现有功能、身份、数据和恢复语义。实施前先提交本文；每阶段验证后单独提交。测试仅使用隔离的合成数据，不读取用户运行数据。

## 1. 范围与约束

当前 AppState 持有 DbPool；SQL 分布于 db.rs、导入、仓库镜像/地址迁移、备注、笔记、备份等模块。config.json 已是 JSON，但路径和测试仍依赖连接池。metadata.rs 与 notebook_repository.rs 延迟创建的表也在迁移范围。

技能正文、脚本、附件、图标、外部 Markdown 笔记保留原格式。全部 JSON 指替换数据库持久化，不把资源文件编码进 JSON。保留 IPC 契约、前端布局、产品及安装升级标识、.skillshub 目录名。安装与卸载继续复用 linker 的业务实现。

| 数据域 | 必须保留 |
| --- | --- |
| skills | 稳定 ID、路径、名称、描述、来源分类、扫描时间、已有 content |
| skill_sources / skill_source_syncs | 来源、版本、指纹、检查/更新时间、删除与错误状态 |
| skill_metadata | 标签、备注、更新时间、现有匹配规则 |
| skill_installations | 平台、安装路径、链接类型、目标、is_managed、首次安装时间 |
| agent_skill_observations | 稳定行身份、原生/只读来源、观测路径 |
| agents | 平台配置投影、检测状态、共享中心及项目目标 |
| collections / collection_skills | 集合身份、成员、加入时间、排序语义 |
| github_repository_stats | 仓库键、星数、检查时间 |
| repository_local_directories | 仓库目录映射、目录唯一性与大小写行为 |
| repository_mirrors / repository_mirror_snapshots | 镜像引用、快照、摘要、状态、时间 |
| repository_mirror_recovery | 恢复数据，不作为普通缓存删除 |
| repository_address_moves | 迁移日志及提交状态 |
| import_transaction_receipts | 文件事务对应的持久提交凭据 |

现有 SkillInstallation 查询模型缺少 is_managed，不能直接当作完整导出模型。SQL NOCASE、Unicode 标签比较、路径比较分别按原语义实现，不能统一替换成小写比较。

## 2. 目标结构

Tauri 命令与业务流程 → 业务存储接口 → JSON 持久化及内存索引。AppState 最终持有 AppStore。接口表达查询、扫描批次、标签批量修改、导入提交、所属记录删除等行为；不向业务模块暴露 JSON 文件或可随意修改的全局状态。

拟定模块：storage/models.rs（持久模型与约束）、store.rs（快照/写入）、indexes.rs（索引）、persistence.rs（提交/版本）、operations.rs（文件操作恢复）、migrations.rs（JSON 格式升级）。过渡适配层允许暂存，但最终删除 DbPool、SQL executor 参数和多余转发。

## 3. 文件布局与提交协议

```text
.skillshub/
  config.json
  store/
    manifest.json
    manifests/<revision>.json
    objects/<object-id>.json
    operations/<operation-id>.json
    staging/
    store.lock
```

manifest 保存格式版本、revision、上一 revision、数据域到对象的引用、对象校验和与提交身份。对象不可变；小记录按数据域分组，大笔记、解释、镜像 payload 分离，具体分片由实测调整。

提交顺序：基于当前版本生成变更 → 约束校验 → 写变更对象并持久化 → 写并验证新 manifest → 原子发布当前 manifest → 发布内存快照 → 返回成功 → 延后回收旧对象。读者只看到完整旧版本或完整新版本。

原子可见性与断电持久性分别测试，Windows/macOS/Linux 文件替换语义分别验证。回收必须保留当前/恢复版本、活动备份及未完成操作引用。读取损坏不能写入空默认数据；权威数据进入受限恢复状态，缓存可按域重建。回退 manifest 需同时检查文件操作日志。

config.json 保留路径与格式，独立原子保存；涉及配置和业务元数据的联合变更由持久操作日志协调。

## 4. 内存与并发

建立技能 ID、平台安装/观测、集合成员及反向关联、仓库、路径、标签索引。大正文及快照按需读取。查询使用已提交快照；统一写队列和数据目录进程锁避免丢更新。网络、下载、扫描在提交锁外执行，提交时验证 revision 和业务前提，不能用过期整条记录覆盖新备注。

扫描采集结果后按范围批量提交，只有完整成功的范围可以清理过期记录。取消、权限错误和部分失败不能导致误删。核心编辑持久化成功才返回；缓存允许合并写，但不能弱化用户编辑的保存语义。

## 5. 文件操作恢复

日志记录操作 ID、类型、基础 revision、目标及归属、staging/回滚材料、阶段、提交凭据。流程：持久化准备日志 → 准备文件 → 执行可恢复变更 → 提交元数据与凭据 → 清理。

未改目标时可清理或继续；文件已改但未提交时按原业务回滚/续做；已提交时只完成剩余步骤，不重复导入。外部修改或归属不明时保留现场并停止受影响操作。

重点覆盖导入文件事务、镜像应用/失败恢复、地址迁移（来源、实际目录、链接、笔记绑定）。维持技能 ID 和仓库 UUID。启动先锁目录、校验/加载、恢复，再开放写入。

## 6. 迁移和备份

独立一次性工具读取旧 SQLite，最终主程序不包含 SQLite 读取依赖。旧程序停止写入后建立一致备份，识别延迟表及未完成事务；先恢复稳定状态或拒绝迁移。读取包含 WAL 已提交数据的一致快照，输出独立 staging，逐项验证记录、字段、引用、身份、唯一性和查询结果，再发布完成标记。保留原数据库归档，不双写。

有效 JSON 已存在时不可被旧数据库覆盖；失败可重试；新 JSON 已产生编辑后不能直接回退到过时数据库。现有 AppBackup 非全数据库快照，不作为完整迁移输入替代。保留旧逻辑备份导入、本地与 WebDAV 现有范围，不扩大同步范围。

目录切换需冻结写入、复制一致版本和必要恢复材料、验证目标、最后切换指针；不能再以 db.sqlite 存在为有效目录依据。

## 9. 验证策略

保留现有业务断言；以存储故障注入替代 SQL 触发器失败夹具。运行前后端测试、类型检查、lint、Rust clippy、构建；失败区分既有问题和本次回归。UI 和真实 OS 行为不能用构建成功代替。

合成数据档位 1k/10k/50k 技能，组合安装关系、平台观测、集合、笔记与解释体积。记录冷/热启动、查询 p50/p95、单条和批量编辑、扫描/导入、备份恢复、峰值内存、写入量及文件数。网络耗时与持久化耗时分离。

待基线确认的目标：常用查询 p95 ≤ 1.2×基线，编辑持久化 p95 ≤ 1.5×，本地扫描/导入持久化 ≤ 1.3×；结合绝对耗时评估。已返回成功的核心编辑在进程异常终止后可恢复。断电测试单列，不混同强杀。

故障矩阵：临时写失败、对象持久化后中断、manifest 发布前后中断、文件移动后未提交、提交后未清理、重复恢复、磁盘满、锁冲突、数据损坏、外部目标被修改。

## 10. 最终移除检查

主程序无 sqlx/SqlitePool/DbPool/SQL 查询、Tauri SQL 插件及权限；锁文件和传递依赖已验证。无 checkpoint/数据库复制/数据库路径判断；测试不创建数据库；构建辅助 prepare_config_dir 和打包脚本同样覆盖。正常运行不创建或更新数据库及 sidecar。旧文件识别仅用于迁移提示，迁移工具独立。更新架构文档及错误提示；不修改产品标识。

## 当前运行架构

React / Zustand → 原有 Tauri IPC → Rust 领域接口（db 命名空间）→ AppStore / JSON 文件。IPC 命令及 DTO 保持兼容；config.json 继续保存设置、平台和项目，技能与附件仍留在原资源目录。

配置目录新增 `store/manifest.json`、`store/objects/<sha256>.json` 和 `store/manifests/<revision>.json`。manifest version=1，一次指定所有领域的对象版本；对象是以领域主键为键的 JSON map。技能等单键直接使用 ID，关系使用 JSON 数组字符串复合键，仓库比较使用 ASCII 大小写规则，笔记序号另存 store_counters。对象不可原地编辑，手工改内容会触发摘要检查失败。所有业务写入应通过应用完成。

`.store-access.lock` 与 `store/store.lock` 是进程排他锁；锁文件存在不代表被占用。不要删除正在使用的锁文件。损坏时保留整个目录并从经过验证的备份恢复，不以空目录覆盖故障数据。


### P7 性能续进（2026-10-17）

持久层在保留独立历史副本、同步落盘、摘要校验和原子发布的前提下，采用有界写入流水线、跨领域并行加载和重复对象共享。数据格式保持 v1，已有存储无需迁移。同机常规保存 p95 改善约 28%–35%，10k/50k 重开约改善 46%/27%；小数据量重开及部分查询指标未改善，原相对 SQLite 保存门槛仍不满足。

新增密集备注/64 KiB 大正文基准揭示 50k 元数据整表保存仍约 586ms（debug）。进一步优化需单独评估分片及兼容恢复方案。完整实测、波动、回归及未验证边界见 [验证记录的 P7 续进章节](JSON存储实施验证记录.md)，不将本轮推进标为全部 P7 发布验收完成。


### P7 续进：密集备注分片（2026-10-18）

为解决 50k 密集备注保存时的整表复制与重写，新增 `storage/table.rs` 逻辑表封装。普通表保持原单对象布局；`skill_metadata` 达到 8,192 条后在可变访问时采用 256 个稳定分片，分片号为完整主键 UTF-8 字节的 SHA-256 首字节（0–255）。小表保持单文件，已分片表缩小后不自动合并，避免格式反复切换。

内存以 `Arc` 共享各片，普通单条修改仅复制所属片；全量遍历与逻辑 JSON 导出保持原有主键排序。磁盘每片仍是带 SHA-256 内容标识的不可变 JSON map。manifest v2 在原 `tables` 外增加 `shards.skill_metadata`（分片号 → 对象摘要），同一表不得同时出现在两处；其他领域暂不分片。分片对象、其他脏表和两份独立 manifest 均持久化后，才发布一个当前 manifest，维持跨表/跨片原子性。

新程序兼容 v1；打开旧大表只转换内存结构，不改当前 manifest。首次修改备注表时一次性写出分片并发布 v2，失败保留旧已提交版本；后续编辑复用未变分片。v1-only 旧程序会因版本号拒绝读取 v2；不能通过手改版本号回退。离线 SQLite 迁移工具仍输出 v1，由新程序按上述规则接入。

清理仍先验证全部恢复历史及引用，保留最近两版。通过一次目录枚举验证对象存在性，避免对每个分片反复做独立文件属性查询。分片摘要、分片归属、缺失对象、冲突表声明均在加载时验证。缓存对象已被历史清理时，从仍完整的内存快照重建对象后再提交，不复用悬空引用。

新增阈值、逻辑表行为与快照隔离、v1 转换失败重试、单片更新范围、删除/清空、损坏/错片拒绝、跨表故障及旧快照重存测试，并让实际备份恢复、目录迁移、发布前/后强杀测试覆盖分片。基准记录稳态保存、对象写入字节、重开及首次 v1 转换成本，实测结论见验证记录。本轮不声称解决全表批量改写、真实断电或所有跨平台验收。


2026-10-18 最终复测：50k 密集备注稳态保存 p95 从 550.8ms 降至 10.7ms（三轮中位数），一次编辑备注对象从约 14.9MB 整表变为约 46KB 分片；首次 v1 转换约 645ms。Rust 581 项及配置工具 2 项、前端 813 项等完整回归通过。部分普通查询的组合基准仍变慢，未标记全部性能门槛通过；完整数字、限制及原始 CSV 见验证记录。


### P7 续进：查询和批量路径（2026-10-18）

以 `0cefcc6` 为起点复测后，优化普通查询的 JSON 中间克隆、平台查询不返回字段的字符串分配、批量标签的线性选择查找，以及重开时外层 BTreeMap 的逐行构建。查询保持原字段校验和顺序；标签使用 HashSet 判断选中范围但仍按原表顺序处理，整批单事务提交；加载仍先验证完整对象摘要，再解码及验证分片。持久化协议、v1/v2 兼容、8,192 门槛、256 分片、同步落盘和恢复历史保持不变。

本轮三轮组合基准中位数：50k 平台查询 216.8 → 184.6ms、合集查询 26.2 → 23.1ms、普通重开 488.4 → 439.2ms；选中一半技能的批量标签添加 5.21 → 0.54s、删除 5.37 → 0.64s。密集备注保存保持 10.55ms / 单个 46,210 字节对象。初始批量导入没有明显改善，小表保存仍波动，新增解码向量的峰值内存未实测；不标记全部 P7 门槛完成。Rust 584 项及配置生成 2 项、前端 813 项等完整回归通过，完整方法、边界和原始数据见 [验证记录](JSON存储实施验证记录.md) 及 [CSV](benchmarks/json-storage-p7-queries-windows.csv)。
