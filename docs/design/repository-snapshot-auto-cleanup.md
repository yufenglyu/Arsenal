# 仓库快照缓存自动清理

日期：2026-10-19。

## 清理时机

- 启动后，等待持久化任务及检查报告加载完毕，回收无引用快照。
- 报告、任务完成状态或清除状态变化后，合并短时间内的事件再清理；另每 5 分钟补查一次，处理之前失败的清理。
- 检查步骤开始前，沿用现有的引用核对及旧缓存压缩。
- 仓库更新全部写入并验证成功后，在同一 Store 事务中标记已应用，释放快照内容及恢复日志，保留小型完成记录供丢失响应后的重放使用。
- 写入后预计达到 1 GiB 限额的 80% 时，优先释放已完成负载；清理后仍超过限额则报告容量不足，不驱逐尚有用途的快照。

## 保留与并发规则

当前报告引用的快照，以及未成功且未明确清除的应用任务引用的快照，均保留。失败、取消、暂停或中断后可重试的任务不会按时间直接过期。

自动清理避开正在检查、应用或迁移的时段。先取得后端快照 ID 清单，再重新读取当前任务和报告引用，只释放清单中已无引用的 ID。清单返回后开始的新任务会使该轮清理退出，新创建的快照也不会进入旧清单。后端通过镜像互斥锁串行化操作，并在释放事务中保护 applying 状态和恢复日志引用。

只有已提交的 applied 状态证明恢复负载可以释放；失败的应用仍保留负载。已完成的小型记录可在失去报告和任务引用后回收。

清理失败不影响业务任务，稍后重试。界面不增加弹窗或维护任务。维护经 Store 接口提交，沿用存储层的双版本恢复历史及对象回收；逻辑缓存释放后，磁盘上的上一版对象可能暂时保留用于恢复。

## 实现与验证

- 前端入口：`App.tsx` 挂载 `snapshotCacheMaintenance.ts`，卸载时取消订阅及计时器。
- 后端：`repository_mirror.rs` 管理完成负载、容量检测和事务释放。
- 新增 8 项前端测试，覆盖加载时机、当前引用、重试任务、并发检查、报告清除、失败重试和卸载。
- 新增 3 项后端测试，覆盖成功应用后释放与幂等重放、容量保护、释放时再次检查恢复状态。
- 完整回归：前端 84 个文件、853 项通过；后端 603 项通过、15 项默认忽略。类型检查和正式代码 lint 通过；lint 排除既有原型文件。
- 前端生产构建通过，保留既有大 chunk 提示。自动清理逻辑通过测试验证；未将这些结果等同于所有远端仓库更新成功。
- Tauri release 构建通过，已部署至指定便携目录。替换前备份可执行文件和完整 Store，逐文件核对备份，安装文件与构建文件 SHA-256 一致。
- 启动后进程有响应，原有 2 份快照、1,471,020 字节负载保留。本次启动没有可供回收的旧快照，因此启动实测只证明正常运行及现有缓存保留；自动回收的各个分支由上述回归测试验证。未自动发起仓库更新或应用远端变更。
