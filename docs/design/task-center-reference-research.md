# Arsenal 任务交互参考研究

检索日期：2026-10-19。只依据第一方文档和官方产品文章。下列“已确认”是来源明确描述的行为，“借鉴建议”是面向 Arsenal 的设计判断；没有对这些产品做本机实测。旧版官方截图用于讨论结构，不代表当前版本的逐像素外观。

## 判断

建议下一轮优先探索 **底部可收起的任务队列 + 按需展开明细 + 专门的业务确认视图**。这是综合下列案例后的设计推断，不是任何一家产品直接给 Arsenal 的规范。

问题应先从职责划分入手：后台进度回答“现在做什么”，异常回答“哪里失败”，业务确认回答“允许哪些变更”。三者同时铺在一个大弹窗里，会让用户在查看进度时也承担处理和诊断的阅读成本。

## 1. WinSCP：底部后台队列，最接近批量导入和更新

**已确认：**底部队列可以显示/隐藏，默认空队列隐藏。一条记录代表一次后台操作而不是一个文件；批量操作分别展示总进度和当前文件。需要交互时，既支持自动提示，也支持只标记对应记录，由用户主动打开处理。队列还提供取消和清理已完成记录等操作。[官方队列文档](https://winscp.net/eng/docs/ui_queue)

**借鉴建议：**Arsenal 一行表示一次导入、检查或更新批次，展开后看仓库/技能明细；状态栏给出活动任务数和待处理数。等待确认只标记任务，由用户打开选择或变更审阅。收起队列后仍能操作技能仓库。

**不宜照搬：**文件传输的速度、字节数、连接优先级并非技能任务的常用信息；不要把批次数字、仓库数字、技能数字放进同一统计。是否支持暂停，应服从执行器能力，不能只因参考产品有该按钮就添加。

**视觉资料：**上述文档明确描述底部布局，但本次没有将该页记录为已核实的独立产品截图来源。

## 2. JetBrains/PyCharm：状态栏入口与后台进程列表

**已确认：**耗时操作可以在后台进行；点击状态栏或从菜单打开 Processes，查看当前后台进程的进度，并取消允许取消的进程。自动打开列表是可配置行为。[PyCharm Processes 官方帮助](https://www.jetbrains.com/help/pycharm/working-with-processes.html)

**借鉴建议：**平时仅在状态栏呈现摘要；主动打开后优先显示正在执行的任务及当前阶段。取消操作应该和任务能力绑定，状态明确显示“正在停止”，不能点完立即伪装成已结束。

**不宜照搬：**纯进度列表不足以承载导入选择、冲突处理和更新差异；这些应有独立处理空间。

**视觉资料：**帮助页包含 Status bar、Show processes、Processes 三处示意；另有 [JetBrains 官方后台任务截图](https://resources.jetbrains.com/help/img/idea/2026.2/project_analysis_process_background_tasks.png) 可用于结构讨论。

## 3. Chrome：近期任务轻入口与完整记录分层

**已确认：**2023 年官方下载体验改版采用地址栏旁托盘、进度环、近期下载列表和行内操作；保留“显示所有下载”进入完整记录。文章同时说明可以关闭自动展开。当前帮助页仍说明托盘、暂停/恢复/取消以及下载历史入口。[Chromium 官方改版说明](https://blog.chromium.org/2023/08/redesigning-chrome-downloads-to-keep.html?version=published)、[Chrome 官方帮助](https://support.google.com/chrome/answer/95759?hl=en)

**借鉴建议：**最近任务和长期历史分层；一条任务只突出当前有用的操作，例如失败时重试、待确认时处理。成功任务没有必要永久占满首屏。

**不宜照搬：**小托盘适合快速查看，却容不下复杂技能选择和差异审阅；不能把上一轮的大弹窗等比例缩进一个窄抽屉。24 小时历史窗口也不能未经讨论直接套用。

**视觉资料：**本次核实的是上述官方文字行为，没有核实可单独引用的下载托盘截图，勿把重绘草图标成 Chrome 截图。

## 4. Docker Desktop Builds：任务与诊断详情分层

**已确认：**运行中构建与构建历史分开；选择构建进入详情。日志支持实时更新，步骤列表可以折叠，也可切换纯文本；失败时错误视图定位出错步骤。[Docker Builds 官方文档](https://docs.docker.com/desktop/use-desktop/builds/)

**借鉴建议：**任务概要展示结果和当前阶段，诊断信息按需展开。失败应优先呈现失败对象、原因摘要及下一步，完整日志是二级入口。

**不宜照搬：**构建时序图、缓存统计和多个技术页签对于 Arsenal 日常任务过重；不要把复杂诊断工具变成所有任务的默认外观。

**视觉资料：**[官方 GA 介绍](https://www.docker.com/blog/announcing-builds-view-in-docker-desktop-ga/) 的 Figure 1 为错误日志、Figure 2 为错误步骤上下文、Figure 3 为历史列表。这是 2023 年发布截图，仅用于观察层次结构。

## 5. 两组补充规范

VS Code 的 [Panel 官方指南](https://code.visualstudio.com/api/ux-guidelines/panel) 将面板用于需要横向空间的辅助功能，并明确提醒用户经常收起面板；页面附有面板和工具栏截图。由此推断，任务队列适合放在可收起的底部面板，但待处理提醒必须在面板关闭后仍可被发现。

- **VS Code：**官方建议后台进度使用低干扰的状态栏入口；进度尽量留在相关视图中，模态框只用于需要立即输入的情形，避免重复通知。[状态栏指南](https://code.visualstudio.com/api/ux-guidelines/status-bar)、[通知指南](https://code.visualstudio.com/api/ux-guidelines/notifications)。两页均有官方图片。对 Arsenal 的启发是状态栏摘要和任务面板承担日常反馈，通知只提示值得注意的状态变化。
- **GitHub Actions：**官方区分重跑全部、失败作业和特定作业。[官方重跑说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)。对 Arsenal 的启发是明确重试范围；“仅重试失败项”与“重新执行整个任务”应有不同文案和执行语义，实际能否安全重试须由后端确认。

## 下一轮原型应验证的交互

1. 默认仍能看见并操作技能仓库；底部状态栏显示“2 项进行中 · 1 项待处理”等明确的批次数量。
2. 打开队列后，每行只给操作名称、对象、阶段/结果和一个主要操作。日志、错误详情及批次成员按需展开。
3. 导入待确认显示“选择技能”，更新待确认显示“审阅变更”；进入专门视图，返回队列保持位置与选择。
4. 已完成记录可折叠和清理；清理只影响展示历史，不应暗示删除资源或回滚业务操作。
5. 停止经过“请求停止 → 正在停止 → 已停止”；失败显示成功与失败数量，重试范围明确。
6. 所有示例使用虚构仓库与技能，不显示真实配置、个人路径或业务数据。

以上为待讨论方案，未更改正式任务功能；还需要在原型中验证底部队列对技能仓库可用高度的影响，以及大量任务、长名称、窄窗口、键盘操作和明暗主题下的可读性。
