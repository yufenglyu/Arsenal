# 仓库检查大面积失败：诊断与修复

日期：2026-10-19。

## 结论与证据

主要故障发生在下载之后的本地快照持久化阶段，并非技能源数据整体损坏。停止时已处理 68 个仓库：62 个为 `SNAPSHOT_CACHE_FULL`，2 个为不支持的远端文件类型，1 个网络失败，1 个快照内容不完整，2 个成功。其余仓库未完成检查，不能推断结果。

本地快照表有 47 份记录、36 个仓库，负载合计 1,073,740,688 字节，几乎达到代码规定的 1 GiB 上限。45 份记录来自此前检查，当前报告只引用 2 份。字节数组的 JSON 编码放大了存储占用；无变化检查也保留整份内容，重复检查还会产生新 ID。前端只识别对象形式的错误码，仓库报告返回字符串错误码时落入通用提示。

## 修复

- 新快照采用 gzip/base64 编码；兼容读取旧 JSON，校验持久化摘要，限制解压后大小。旧快照升级保持 ID 和内容不变。
- 相同的已检查负载复用 ID；无变化检查只保留已检查的提交号，不保存整份应用负载。
- 每个检查步骤执行前，以当前报告及未完成应用任务计算保留 ID。回收无引用快照，始终保护 applying 状态和恢复日志引用。
- 错误映射同时支持字符串和对象形式，展示容量、路径及快照完整性的明确原因。
- 增加受 feature 控制的离线 `snapshot_maintenance` 工具，只通过事务 Store 维护缓存，不修改技能目录或内容寻址对象。

## 本地处理

程序退出后，先备份原可执行文件和完整 Store。事务压缩后逐份解压比较：47 份内容完全一致，其他数据表引用不变。再依照当前报告回收 45 份无引用缓存，保留 2 份；负载最终为 1,471,020 字节。再次确认保留内容完全一致，其他数据表及分片引用不变。

修复程序已构建并替换至指定便携安装目录，源文件与安装文件 SHA-256 一致。保留备份以便回退；回退旧程序需同时恢复对应 Store，不能仅替换旧 exe 后使用新编码缓存。

## 验证与边界

- 回归用例先复现了重复检查累积以及字符串错误码退化的问题，修复后通过。
- 前端：83 个测试文件、845 项通过；类型检查与正式代码 lint 通过（排除已有两个原型文件的热更新警告）。
- 后台：600 项通过，15 项默认忽略；另显式运行真实网络检查。
- 两个原失败公共仓库分别完成版本解析、下载、远端校验、持久化和解码一致性检查。其中一次匿名额外复验遇到 GitHub HTTP 403、剩余额度 0；改用程序现有访问配置后同一检查通过。未输出或保存凭证。
- Tauri release 程序构建成功。构建仍提示前端大 chunk。
- 未自动应用任何仓库更新，也未宣称全部 103 个仓库已通过；旧报告需重试。远端不支持的文件类型及不完整下载仍由安全校验阻止，不绕过校验强制同步。
