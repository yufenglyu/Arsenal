### 必须保持的行为契约

1. `upsert_skill`：已有 central 记录遇到非 central 重扫时保留名称/正文/路径/来源，不降级；缺省 canonical_path 保留已有值；更新扫描时间。
2. 资源库查询条件是非 central 且 canonical_path 非空，并按名称排序。JSON 必须复现条件及显式排序；无 ORDER BY 的查询不承诺偶然的 SQL 返回顺序。
3. 托管安装更新不改 created_at；扫描发现不能覆盖已有托管记录的路径、链接和归属。持久模型必须包含 is_managed。
4. 启动计算项目序号下限，考虑安装和观测中已有 project ID，配置重置不能导致身份复用。
5. 技能删除存在不同范围的入口；保留各自的关联清理语义，不能统一成删除所有相关资源。中心移除不删资源库原文件。
6. 来源检查时间更新不覆盖已安装 remote_ref、fingerprint 或 last_sync_at。
7. 标签保留现有 trim/长度约束和大小写比较；仓库 SQL NOCASE、路径比较不能用同一规则替代。
8. 笔记 restore 可重分配本地整数 ID，但保留 repository_uid 和 source_key；唯一绑定检查、正文长度和 expected_body 冲突检查保持。
9. 镜像地址迁移保持成员 ID、集合、标签、笔记和安装链接；存在冲突或未恢复事务时禁止覆盖目标。
10. 备份 included 范围和 WebDAV 仓库范围保持；备份不是全部内部事务状态的替代导出。
11. IPC DTO、字段命名、空值和错误映射保持；内部持久类型与 DTO 分离。
12. 不把未完成/失败扫描范围当作空集合清理。部分操作失败保持已有错误展示与可恢复状态。

## P7 续进：50k 密集备注的分片增量保存（2026-10-18，Windows）

### 实现与数据安全

- 只对大 `skill_metadata` 表启用 256 个稳定哈希分片；8,192 条以下的新表保持单对象。内存和磁盘同时分片，普通单条编辑只复制、序列化并写入所属片，其他片复用内容摘要。全量逻辑遍历仍按原主键顺序，普通表遍历不分配迭代器堆对象。
- 首次修改旧 v1 大表时发布 v2。仅打开不改现有 manifest；其他表的修改也不主动迁移备注表。新程序可读 v1/v2，v1-only 旧程序拒绝 v2。逻辑备份格式不变；离线 SQLite 工具继续输出 v1。

## P7 续进：普通查询、批量标签和重开（2026-10-18，Windows）

### 复现与结论

本轮以 `0cefcc6` 分片实现为起点，先重新执行组合基准和独立进程的普通基准。50k 平台查询分别为 216.8/223.4ms，普通重开为 488.4/503.7ms；没有稳定复现上一轮组合运行的 241.7/616.4ms。因此不能把历史两次运行之差全归因于分片，也不能用较慢的历史值夸大本轮收益。以下主要对比本轮优化前实测。

确认并优化的成本：

1. 普通 `rows`、单条与合集读取先深拷贝 JSON Value，再构造业务 DTO。改为从 `&Value` 反序列化，仍返回独立拥有数据的 DTO。平台查询使用借用字段视图，避免复制不会返回的 Markdown 正文、规范路径及安装关联字段；字段类型、必填规则、安装筛选和输出顺序不变，并把循环中不变的表查找移到循环外。
2. 标签批量选择对每条技能执行 `Vec::contains`，50k 技能选一半时为平方级查找。改为一次构造 HashSet 查找，仍按技能表原顺序处理；重复/不存在 ID、空选择、全选及大小写规则不变。标签规范化只计算一次，备注读取取消中间 JSON 克隆，整批仍在一个事务中提交。
3. 重开反序列化外层表时逐条插入 BTreeMap。改为收集已解码行后批量构建有序表，避免每行独立查找/再平衡。对象字节先做完整 SHA-256 校验再解码，分片归属和 manifest 校验沿用原流程；v1/v2 格式、锁、落盘屏障、原子发布及历史清理均未改变。临时行向量会带来额外容器内存，未声称峰值内存下降。

尝试减少每次 `table_mut` 的脏标记/表名分配，收益不明确，未保留。普通整批导入尚无明显提速，不将标签批量收益泛化为所有批量操作。

## P7 续进：普通批量导入与小表保存分布（2026-10-18，Windows）

### 定位与实现

本轮承接 `b0bc61f`。先给原普通导入基准增加构造记录/提交两个分段计时，数据量、业务调用和计时边界没有缩减。50k 前测三轮中位数：构造 377,783μs、提交 996,880μs、总计 1,444ms（各列分别取中位数，不能相加重构总计）。提交是主要成本；原实现只并行写文件，大表 JSON 编码及 SHA-256 仍在调用线程逐表执行。

现在只对**至少两张、各不少于 8,192 行、需要重写的普通表**并行编码，最多两个编码任务在途；按原有序表顺序消费结果，继续由调用线程统一按摘要去重，再交给原有最多两个对象写入任务。相同内容的两张表不会竞争同一个 pending 文件。单张大表、小表和密集备注分片不启用新增编码线程。新增路径没有改记录构造、查询、标签业务逻辑，也没有新增磁盘格式。

所有编码任务在作用域内结束；对象和两份独立 manifest 仍须同步完成后才原子发布。既有 SHA 校验、内容冲突拒绝、分片归属、v1/v2 兼容、进程锁、最近两版历史和清理策略保持不变。失败不发布半批数据。代价是额外的有界编码缓冲：最多两个编码任务、两个原有写入任务及调用线程当前缓冲；峰值内存未实测，不声称内存占用不变。
